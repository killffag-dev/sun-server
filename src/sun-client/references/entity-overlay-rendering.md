# Кастомная 3D-геометрия поверх сущности (FeatureRenderer) — уроки из China Hat

Этот файл — накопленный опыт отладки `HeadCosmetics` / `ChinaHatFeatureRenderer` (конус-шляпа поверх головы игрока, `FeatureRenderer<PlayerEntityRenderState, PlayerEntityModel>`, без текстуры, рисуется напрямую через `Tesselator`+`BufferRenderer.drawWithGlobalProgram`, не через `vertexConsumers`). Если новый `FeatureRenderer` рисует произвольную геометрию (конус, коробку, кольцо и т.п.) поверх сущности таким же способом — сначала прочитать этот файл, чтобы не повторять уже пройденные баги.

**Читать перед**: добавлением нового `FeatureRenderer` с ручной отрисовкой геометрии (не через готовые `ModelPart`/текстуры), любым багом вида "часть сущности пропадает/мерцает рядом с кастомным оверлеем", вопросами про `depthMask`/`vertexConsumers`/z-fighting в контексте рендера сущностей.

---

## 1. TRIANGLE_FAN вместо набора несвязанных TRIANGLES

Если фигура — веер треугольников с общим центром (конус, диск-основание и т.п.), собирать её как `DrawMode.TRIANGLE_FAN`, а не как отдельные `DrawMode.TRIANGLES` с дублированием вершин на общих рёбрах.

Причина: при альфа-блендинге (полупрозрачная геометрия) независимые треугольники с дублированными вершинами на общем ребре дают заметный шов — на скриншоте это выглядит как радиальные линии от центра к краю фигуры. `TRIANGLE_FAN` делает рёбра действительно общими на уровне вершин, шва нет.

```java
BufferBuilder sideBuffer = RenderSystem.renderThreadTesselator().begin(DrawMode.TRIANGLE_FAN, VertexFormats.POSITION_COLOR);
sideBuffer.vertex(m, 0, -HEIGHT, 0).color(r, g, b, a); // вершина/центр веера
for (int i = 0; i <= SEGMENTS; i++) {
    sideBuffer.vertex(m, ringX[i], 0, ringZ[i]).color(r, g, b, a);
}
```

## 2. У фигуры должно быть "дно" — иначе сквозь неё видно то, что она должна закрывать

Конус/коробка/любая незамкнутая фигура без нижней (или другой открытой) грани — это дыра, сквозь которую под определённым углом обзора виден объект внутри (например, голова игрока сквозь шляпу-конус без дна).

Фикс — рисовать отдельный `TRIANGLE_FAN` для основания, с обходом вершин **в обратном порядке** относительно боковой поверхности (иначе нормаль "смотрит" не в ту сторону и грань не видна с нужного ракурса при `disableCull()`/`enableCull()`):

```java
BufferBuilder bottomBuffer = RenderSystem.renderThreadTesselator().begin(DrawMode.TRIANGLE_FAN, VertexFormats.POSITION_COLOR);
bottomBuffer.vertex(m, 0, 0, 0).color(r, g, b, a); // центр дна
for (int i = SEGMENTS; i >= 0; i--) { // обратный порядок!
    bottomBuffer.vertex(m, ringX[i], 0, ringZ[i]).color(r, g, b, a);
}
```

## 3. Оверлей должен сидеть с запасом НАД реальной геометрией, а не над "голым" мешем

Если оверлей крепится к части тела (голова, торс и т.п.) через локальные координаты этой части (`ModelPart.rotate(matrices)` + `translate`), не рассчитывать отступ (`Y_OFFSET` и т.п.) от размеров голого куба модели. Учитывать, что:

- у скина есть overlay-слой (второй, чуть увеличенный слой — "hat layer" для головы), который выступает над базовым кубом на 1-2px;
- если на этой части тела может быть надета броня — физическая модель брони ещё больше, чем overlay-слой скина.

Отступ, рассчитанный впритык к голому кубу, будет либо протыкать оверлей (виден "квадрат" сквозь полупрозрачную фигуру), либо давать z-fighting с бронёй (см. п.5). Закладывать отступ с запасом, ориентируясь на скриншот с надетой бронёй, а не только на голый скин.

## 4. depthMask и enableDepthTest — это РАЗНЫЕ вещи, не путать

- **`RenderSystem.enableDepthTest()`** — тест глубины: не даёт рисовать оверлей поверх того, что физически ближе к камере (стены, блоки). Это то, что защищает от "просвечивания сквозь стены". Держать всегда включённым для 3D-оверлея в мире.
- **`RenderSystem.depthMask(true/false)`** — запись глубины: определяет, будет ли наш оверлей влиять на то, что рисуется **после** него в этом же кадре. Это не про стены, это про порядок относительно других объектов сцены (броня, предмет в руке и т.п.).

Не трогать `depthMask` в попытке починить "просвечивание сквозь стены" — за это отвечает `enableDepthTest`, а не `depthMask`. `depthMask` может понадобиться выключить/включить только из-за проблем п.5.

## 5. Гонка с батчингом `vertexConsumers` — самая коварная проблема

### Симптом
Надетая на сущность броня (в частности шлем) и/или предмет в руке **периодически пропадают**, когда камера смотрит через/рядом с нашим полупрозрачным оверлеем, причём именно те объекты, что физически близко к оверлею по глубине от камеры. Это выглядит как z-fighting, но обычным сдвигом `Y_OFFSET`/`depthMask` не лечится стабильно — то одна часть пропадает, то другая, в зависимости от того, что трогаешь.

### Причина
Обычные `FeatureRenderer` (броня, предмет в руке и т.д.) не рисуют сразу — они кладут вершины в переданный `VertexConsumerProvider` (обычно это `VertexConsumerProvider.Immediate`), который батчит все фичи сущности и сбрасывает (`draw()`) их одним пакетом в определённый момент кадра.

Наш `ChinaHatFeatureRenderer` (и любой похожий оверлей) рисует **немедленно**, через `RenderSystem.renderThreadTesselator()` + `BufferRenderer.drawWithGlobalProgram(...)`, полностью в обход этой очереди. Даже если наша фича зарегистрирована **последней** в списке фич (через `@Inject(at="TAIL")` в конструкторе рендерера сущности — см. `PlayerEntityRendererMixin`), это гарантирует лишь порядок **постановки в очередь**, а не порядок **фактической отрисовки на GPU**. Наш прямой draw физически попадает в буфер глубины раньше, чем ещё не сброшенный батч брони/предмета. Если у нас включена запись глубины (`depthMask(true)`), и наш оверлей оказывается "ближе" камеры в месте пересечения — то когда чуть позже реально рисуется батч брони/предмета, их фрагменты проваливают тест глубины против уже записанной нашей глубины и не рисуются вовсе.

### Фикс
Перед своей отрисовкой форсировать flush уже поставленных в очередь батчей:

```java
@Override
public void render(MatrixStack matrices, VertexConsumerProvider vertexConsumers, int light,
                    PlayerEntityRenderState state, float limbAngle, float limbDistance) {
    // ...ранние return-проверки модуля...

    // Форсируем flush уже поставленной в очередь геометрии (броня, предмет
    // в руке и т.д.), чтобы она попала в буфер глубины ДО того, как мы
    // начнём писать свою.
    if (vertexConsumers instanceof VertexConsumerProvider.Immediate immediate) {
        immediate.draw();
    }

    // ...дальше как обычно: matrices.push(), трансформы, свой drawCone(...), matrices.pop()
}
```

Это решило проблему полностью в случае China Hat (проверено пользователем в игре) — броня и предмет в руке перестали пропадать.

### Когда потребуется более тяжёлый фикс
Изначально этот форс-флаш полностью решал проблему с бронёй/предметом в руке. Но позже (см. п.6-7 ниже) всплыл **второй, независимый** баг из-за того же `depthMask(false)` — не с бронёй, а с полноэкранным пост-процессом (`Sky`). Из-за него оверлей всё же пришлось переписать через `vertexConsumers.getBuffer(customRenderLayer)` — это больше не гипотетический "запасной вариант", а сделанный и проверенный в игре рефакторинг. Детали и точный рабочий код (готовые `RenderLayer` для этого проекта) — см. п.7.

## 6. Тот же `depthMask(false)` ломает full-screen пост-процесс, читающий глубину (баг с шляпой/нимбом на фоне Sky)

**Подтверждённый баг** (China Hat, Halo — код идентичный): оверлей пропадает, если за головой игрока открытое небо и включён модуль `Sky`.

### Механизм
`Sky` на момент этого бага висел на `WorldRenderEvents.END` (`Sun.java`, `initializeRenderCompatibility()`) — срабатывает **после того как весь мир и все сущности уже отрисованы за этот кадр**. Его шейдер перекрашивает любой пиксель, где depth-буфер == 1.0, считая это "пустым небом".

`ChinaHatFeatureRenderer`/`HaloFeatureRenderer` намеренно не писали глубину (`depthMask(false)`, см. п.4 выше и историю в п.5 — сделано ради ника игрока). Значит если фон за головой — реальное открытое небо (там и так глубина 1.0), после отрисовки оверлея глубина на этих пикселях остаётся 1.0 (оверлей её не переписал). `Sky`, сработав в конце кадра, видит 1.0 и перекрашивает эти пиксели поверх уже нарисованного оверлея.

**Важно**: `getPriority()` у `EventListener<Render3DEvent>` тут **не работает как фикс** — он упорядочивает только слушателей одного и того же события между собой. `ChinaHatFeatureRenderer`/`HaloFeatureRenderer` — это `FeatureRenderer`, часть обычного рендера сущностей, который **всегда** отрабатывает раньше `WorldRenderEvents.END`, независимо от приоритетов.

### Кто в зоне риска
Любая геометрия, которая рисуется во время обычного рендера сущностей (не как отдельный `Render3DEvent`-модуль) и не пишет глубину. Это касается не только кастомных `FeatureRenderer`, но и **ванильного текста ника** (см. п.8) — у него та же природа: рисуется в кадре сущностей, глубину не пишет.

## 7. Промежуточный фикс: переписать оверлей через RenderLayer (сделано, но не устранило корень)

China Hat/Halo (тело тора) переписаны с прямого `Tesselator`+`depthMask(false)` на нормальный `RenderLayer`+`vertexConsumers.getBuffer(...)`. Это устранило конкретно баг с шляпой/нимбом (глубина теперь пишется правильно, оверлей попадает в общий батч), но **не могло решить проблему в общем случае** — ванильный ник сервера (с кастомными health/clan/privilege-индикаторами) продолжил пропадать тем же способом, потому что его рендер — не наш код, миксинить рендер текста ради этого не вариант. Это стало сигналом, что чинить нужно не каждого "нарушителя" по одному, а сам `Sky` — см. п.8.

Технические детали для будущих похожих рефакторингов на Minecraft 1.21.4 (Yarn build.8, до перехода на `RenderPipeline`/переименования в `RenderType` в 1.21.6+):

- `RenderLayer.of(String name, VertexFormat, VertexFormat.DrawMode, int bufferSize, boolean hasCrumbling, boolean translucent, RenderLayer.MultiPhaseParameters)` — **публичный** статический метод, вызывается напрямую, accessor-миксин не нужен.
- `VertexFormat` в этой версии — `net.minecraft.client.render.VertexFormat` (НЕ `com.mojang.blaze3d.vertex.VertexFormat` — это конкретно версии позже 1.21.4/после рендер-рефакторинга).
- `RenderLayer.MultiPhaseParameters.builder().program(...).texture(...).transparency(...).cull(...).lightmap(...).overlay(...).build(false)` — все константы (`RenderPhase.POSITION_COLOR_PROGRAM`, `RenderPhase.NO_TEXTURE`, `RenderPhase.TRANSLUCENT_TRANSPARENCY`, `RenderPhase.DISABLE_CULLING`, `RenderPhase.DISABLE_LIGHTMAP`, `RenderPhase.DISABLE_OVERLAY_COLOR`) — публичные поля `RenderPhase`.
- Если у фигуры несколько независимых `TRIANGLE_FAN`-частей (например бок конуса + дно, см. п.1-2) — **каждой части нужен свой отдельный `RenderLayer`-инстанс**, даже если настройки идентичны. `TRIANGLE_FAN` не поддерживает несколько независимых вееров в одном буфере: второй веер продолжит первый вместо того чтобы начать новый. Разные `RenderLayer`-объекты всегда попадают в разные draw call'ы. `DrawMode.QUADS` этого ограничения не имеет — можно копить сколько угодно квадов в одном `RenderLayer`.
- Рабочий пример для этого проекта — `HeadCosmeticsRenderLayers.java` (`systems/modules/modules/visuals/headcosmetics/`).

## 8. Настоящий корень проблемы: `Sky` физически стоит не в том месте кадра

Проблема из п.6 — не в том, что конкретные оверлеи "неправильно" не пишут глубину (не писать глубину для translucent-геометрии/текста — нормальная, распространённая практика, в том числе ванильная). Проблема в том, что `Sky` **перекрашивает уже полностью готовый кадр** вместо того, чтобы рисовать фон неба ДО того, как на него садится всё остальное.

### Фикс
Перенести `Sky` с `WorldRenderEvents.END` на `WorldRenderEvents.BEFORE_ENTITIES` (Fabric API, порядок событий за кадр: `START → AFTER_SETUP → BEFORE_ENTITIES → AFTER_ENTITIES → ... → END`). `BEFORE_ENTITIES` срабатывает **после вывода непрозрачного террейна, но до отрисовки любых сущностей** — то есть до ников, HeadCosmetics, мобов, вообще всего. `depth == 1.0` в этой точке кадра — по-настоящему надёжный признак "здесь пусто, это небо" (более надёжный, чем на `END`, где так же выглядела бы любая translucent-геометрия без записи глубины).

Через `EventManager` это сделано как **отдельное событие**, а не общий `Render3DEvent` — потому что на `Render3DEvent`/`END` сидят и другие визуальные модули (`Trails`, `FreshDrop`, `TargetESP` и т.п.), которым как раз нужно рисоваться поверх готовой сцены, их трогать было нельзя:

- Новый класс `moscow.sun.systems.event.impl.render.Render3DBackgroundEvent extends Render3DEvent` (только переиспользует поля/геттеры через наследование; `EventManager.triggerEvent` маршрутизирует по точному `event.getClass()`, так что подписчики `Render3DEvent` и `Render3DBackgroundEvent` никогда не пересекаются, несмотря на общего родителя).
- В `Sun.java` — второй `WorldRenderEvents.BEFORE_ENTITIES.register(...)`, триггерящий `Render3DBackgroundEvent`, рядом с существующим `WorldRenderEvents.END.register(...)` для `Render3DEvent` (оба остаются).
- В `Sky.java` — поле переключено с `EventListener<Render3DEvent>` на `EventListener<Render3DBackgroundEvent>`. `getPriority()` больше не нужен (был нужен только чтобы обогнать другие модули на общем `Render3DEvent` — теперь `Sky` вообще не на этой очереди).

**Результат**: этот фикс закрывает проблему полностью и универсально — ник сервера, China Hat, Halo-свечение и вообще любой будущий не-пишущий-глубину оверлей теперь физически не может быть стёрт `Sky`, потому что рисуется поверх уже готового неба, а не наоборот. RenderLayer-рефакторинг из п.7 при этом не стал бесполезным (правильная запись глубины — хорошая практика сама по себе, полезна против других потенциальных будущих проблем), но перестал быть единственной линией защиты.

**Чек-лист при добавлении НОВОГО full-screen пост-процесс модуля** (по образцу `Sky`): если модуль перекрашивает пиксели на основе `depth == 1.0` (или вообще перекрашивает уже готовый кадр поверх всего) — регистрировать его на `WorldRenderEvents.BEFORE_ENTITIES` через отдельный `Render3DBackgroundEvent`-подобный класс, **не** на общий `Render3DEvent`/`END`. Модули, которым наоборот нужно рисоваться поверх готовой сцены (эффекты на сущностях, ESP, трейлы) — остаются на `Render3DEvent`/`END` как обычно.

## Чек-лист при добавлении нового FeatureRenderer с ручной геометрией

- [ ] Форма собрана как `TRIANGLE_FAN` (не разрозненные `TRIANGLES`), если это веер треугольников
- [ ] Есть замыкающая грань (дно/крышка), обход вершин в обратном порядке относительно основной поверхности
- [ ] Отступ от части тела рассчитан с запасом, с учётом overlay-слоя скина и возможной брони на этой части тела
- [ ] `enableDepthTest()` включён (защита от просвечивания сквозь стены)
- [ ] Геометрия рисуется через `vertexConsumers.getBuffer(customRenderLayer)`, а не напрямую через `Tesselator` — см. п.7 (устраняет и гонку с батчингом брони/предмета из п.5, и в принципе не нужен форс-флаш `immediate.draw()`, если это единственная причина его добавлять)
- [ ] Проверено в игре: сбоку (нет щели), сверху (нет дыры/шва), возле стены (не просвечивает), с надетой бронёй (не мерцает), с предметом в руке (не пропадает), на фоне открытого неба с включённым `Sky` (не стирается)
